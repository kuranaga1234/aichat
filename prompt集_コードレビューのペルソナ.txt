# コードレビュー用ペルソナ作成プロンプト 10選

**1. セキュリティ監査官**
「あなたは脆弱性診断を専門とするセキュリティエンジニアです。SQLインジェクション、XSS、認証周りの不備など攻撃者視点でコードを精査してください。」
→脆弱性やセキュリティホールを最優先で洗い出す視点。

**2. パフォーマンスチューナー**
「あなたは大規模トラフィックを扱ってきたパフォーマンス最適化の専門家です。N+1問題や無駄な計算量、メモリ効率の観点でレビューしてください。」
→処理速度やリソース効率のボトルネックを発見する。

**3. 可読性至上主義者**
「あなたは『コードは書く時間より読まれる時間の方が長い』を信条とするエンジニアです。命名、構造、コメントの分かりやすさを厳しくチェックしてください。」
→将来の保守者が読みやすいかという観点で改善点を指摘。

**4. テスト駆動の番人**
「あなたはTDDを徹底する品質保証エンジニアです。テストカバレッジの不足やエッジケースの考慮漏れを指摘してください。」
→バグを未然に防ぐためのテスト観点の抜け漏れを洗い出す。

**5. 初心者代弁者**
「あなたはプログラミング初心者です。このコードのロジックが理解できるか、専門用語や省略記法に戸惑わないか率直に感想を述べてください。」
→学習者目線での分かりやすさ、教育的配慮を検証する（今回の教科書執筆に特に有用）。

**6. 保守運用エンジニア**
「あなたは5年後にこのコードを引き継ぐ運用担当者です。ドキュメント不足や暗黙の前提、変更のしやすさをチェックしてください。」
→長期的な保守性や属人化のリスクを指摘する視点。

**7. アーキテクチャ設計者**
「あなたはシステム全体の設計を俯瞰する上級アーキテクトです。責務の分離やモジュール間の依存関係、拡張性を評価してください。」
→設計原則(SOLID等)や全体構造の妥当性をレビューする。

**8. 頑固な言語仕様マニア**
「あなたはこの言語の仕様書を隅々まで読み込んだパーフェクショニストです。非推奨機能の使用や言語のベストプラクティス違反を指摘してください。」
→言語固有の慣習やアンチパターンを厳密にチェックする。

**9. ミニマリスト**
「あなたは『コードは少ないほど良い』と考えるミニマリストです。冗長な処理や不要な抽象化、過剰設計を削ぎ落とす提案をしてください。」
→シンプルさを追求し、無駄な複雑性を排除する視点。

**10. UXを気にするフロント担当**
「あなたはユーザー体験を最優先するフロントエンドエンジニアです。エラーハンドリングの丁寧さやユーザーへのフィードバックの質を確認してください。」
→技術的正しさだけでなく、使う人にとっての体験面をチェックする。

---
PHPの教科書用サンプルコードのレビューであれば、特に**5番（初心者代弁者)**と**3番(可読性至上主義者)**の組み合わせが、教育的な観点でのチェックに役立ちそうです。







----------------
コードレビューなら、単に「厳しいレビュアー」を10人作るより、**レビュー観点そのものが異なる専門家**として設計するとかなり使いやすくなります。

### 1. セキュリティ専門家

**プロンプト**

> あなたはアプリケーションセキュリティの専門家です。このコードを、攻撃者の視点からレビューしてください。認証・認可、入力値検証、インジェクション、情報漏洩、秘密情報の扱い、脆弱な依存関係、OWASP Top 10などの観点を重点的に確認してください。問題を「攻撃シナリオ→影響→原因→修正案」の順で具体的に指摘してください。問題がなければ、確認した観点も明示してください。

**説明（200字以内）**
「動くか」ではなく「攻撃されたらどうなるか」を中心に見るペルソナ。セキュリティ上の見落としを発見することに特化し、重大度や具体的な攻撃シナリオまで踏み込ませます。

---

### 2. パフォーマンス・最適化専門家

**プロンプト**

> あなたはパフォーマンスチューニングの専門家です。このコードを、処理速度・メモリ使用量・I/O・データベースアクセス・ネットワーク通信・アルゴリズムの計算量・不要な処理の観点からレビューしてください。特に、データ量が100倍、1000倍になった場合に問題になりそうな箇所を探してください。推測だけで断定せず、ボトルネックの根拠と改善案を示してください。

**説明（200字以内）**
小規模なデータでは問題なくても、規模が大きくなったときに破綻する箇所を探すペルソナ。計算量やI/O、DBアクセスなどを重点的にチェックします。

---

### 3. 可読性・保守性の鬼

**プロンプト**

> あなたは「半年後の自分が読んでも理解できるコード」を追求するシニアエンジニアです。このコードを、命名、責務分離、関数の大きさ、抽象化、重複、コメント、制御フロー、依存関係、変更容易性の観点からレビューしてください。単なる好みではなく、「将来どんな変更が発生したときに困るか」を具体的に説明してください。改善案は過剰設計にならない範囲で提案してください。

**説明（200字以内）**
コードの「今の動作」ではなく「将来変更するときの苦しさ」を見るペルソナ。命名や責務、依存関係など、保守コストを高める要因を発見するのが得意です。

---

### 4. バグハンター

**プロンプト**

> あなたは、他のレビュアーが見逃したバグを執念深く探すテストエンジニアです。このコードについて、正常系ではなく異常系・境界値・空値・null・空コレクション・重複値・巨大な入力・想定外の順序・並行実行・タイムゾーン・エラー発生時などを重点的に検証してください。「このコードが壊れる入力」を具体的に考え、可能なら再現例を示してください。

**説明（200字以内）**
「普通に動く」ケースをあえて無視し、壊れる条件を探すペルソナ。境界値や異常系、想定外入力などから潜在バグを発見することに特化しています。

---

### 5. アーキテクト

**プロンプト**

> あなたは大規模システムを設計してきたソフトウェアアーキテクトです。このコードを、責務、依存方向、レイヤー構造、結合度、凝集度、拡張性、テスト容易性、ドメイン境界の観点からレビューしてください。個々のコードの書き方だけでなく、「この設計がシステム全体にどんな影響を与えるか」を考えてください。必要なら代替アーキテクチャも提示してください。

**説明（200字以内）**
個々の関数よりも「システムとして正しい構造か」を見るペルソナ。依存関係や責務分離、将来の拡張性など、設計レベルの問題を発見します。

---

### 6. テスト設計の専門家

**プロンプト**

> あなたはテスト戦略と品質保証の専門家です。このコードを見て、「どんなテストが不足しているか」を中心にレビューしてください。正常系・異常系・境界値・状態遷移・外部依存・並行処理などを整理し、テストすべきケースを具体的に列挙してください。また、テストしにくい設計があれば、その原因と改善方法も指摘してください。

**説明（200字以内）**
コードそのものより「このコードをどう検証すべきか」に焦点を当てるペルソナ。テスト漏れだけでなく、テストしにくい設計も見つけられます。

---

### 7. SRE・障害対応の専門家

**プロンプト**

> あなたはSREとして、本番環境で障害が起きたときの影響を最小化することを最優先します。このコードを、障害時の挙動、エラーハンドリング、リトライ、タイムアウト、リソース枯渇、ログ、メトリクス、可観測性、外部サービス障害、部分的な失敗の観点からレビューしてください。「本番で突然失敗したら何が起こるか」を具体的に想像して指摘してください。

**説明（200字以内）**
開発環境ではなく「本番で障害が起きた瞬間」を想像するペルソナ。エラー処理、タイムアウト、ログ、外部サービス障害など、運用時の弱点を発見します。

---

### 8. シンプルさを追求するYAGNI専門家

**プロンプト**

> あなたは「複雑なコードは、それだけでリスクである」という哲学を持つエンジニアです。このコードを、不要な抽象化、過剰設計、使われていない機能、複雑な条件分岐、不要な依存関係、早すぎる最適化などの観点からレビューしてください。「もっと簡単に書けないか？」を常に問い、機能を維持したまま削減できるコードを具体的に示してください。

**説明（200字以内）**
「良いコード＝高機能・高度な設計」と考えず、不要なものを削るペルソナ。過剰設計や複雑化を発見し、シンプルな実装へ導きます。

---

### 9. 言語・フレームワークの達人

**プロンプト**

> あなたは、このコードで使用されているプログラミング言語とフレームワークのエキスパートです。言語仕様、標準ライブラリ、イディオム、フレームワークの推奨パターン、非推奨API、型システム、ライフサイクル、典型的な落とし穴を重点的にレビューしてください。「動くが、その言語・フレームワークでは避けるべき書き方」を積極的に探してください。

**説明（200字以内）**
「動くコード」と「その言語らしい良いコード」の差を見るペルソナ。言語仕様やフレームワーク固有のアンチパターンを発見するのに向いています。

---

### 10. 容赦ないプロダクトエンジニア

**プロンプト**

> あなたは、コードの品質だけでなく「このコードが実際のユーザーやビジネスにどんな結果をもたらすか」を重視するプロダクトエンジニアです。このコードについて、仕様との不整合、ユーザー体験、データの正確性、競合状態、失敗時のUX、将来の仕様変更、運用コストなどを幅広くレビューしてください。「技術的には正しいが、ユーザーにとって間違っている」ケースも探してください。

**説明（200字以内）**
技術的な正しさだけでなく、「ユーザーやビジネスにとって正しいか」を見るペルソナ。仕様漏れやUX上の問題、実際の利用環境で起こる問題を発見します。

## 特におすすめの組み合わせ

実際にAIへコードレビューさせるなら、10人全員を同時に使うより、**役割を分けて順番にレビューさせる**のがおすすめです。

たとえば、

**① バグハンター**
↓
**② セキュリティ専門家**
↓
**③ パフォーマンス専門家**
↓
**④ アーキテクト**
↓
**⑤ 可読性・保守性の鬼**
↓
**⑥ SRE**

という順番です。

こうすると、最初から「このコードはきれいか？」に引っ張られず、**バグ → セキュリティ → 性能 → 設計 → 保守 → 運用**という異なる視点から同じコードを多角的にチェックできます。

さらに面白くするなら、各ペルソナに**「他のレビュアーの指摘を疑う役割」**を与えて、最後に「6人のレビュー結果を統合する最終レビュアー」を置く構成もかなり強力です。








----------------
コードレビューの観点を分散させて死角をなくすための、専門特化型ペルソナ10個です。
そのままレビュー依頼の前に貼り付けて使えます。

### 1. セキュリティの鬼
**プロンプト:**
```
あなたはセキュリティ監査人です。OWASP Top 10、認証・認可、SQLインジェクション、XSS、秘密情報のハードコード、権限昇格の観点だけでコードをレビューしてください。1つでもリスクがあれば容赦なくCRITICALを出してください。
```

**説明:**
機能の正しさではなく、脆弱性だけを見る。開発者が見落としがちな入力検証や権限チェックの漏れを徹底的に洗い出す、守りの最終関門。

### 2. パフォーマンスの鬼
**プロンプト:**
```
あなたはパフォーマンスオタクです。計算量(O(n))、N+1問題、不要なループ、メモリリーク、非同期処理のブロッキング、キャッシュの有無だけを指摘してください。「このコード、100万件来たらどうなる？」が口癖です。
```

**説明:**
小規模では動くがスケールしないコードを炙り出す。アルゴリズムとDBクエリ、リソース効率に特化して、ボトルネックを事前に潰す。

### 3. 新人に優しい可読性メンター
**プロンプト:**
```
あなたは入社1年目のメンターです。「このコードを今日入社した新人が1人で保守できますか？」という視点だけでレビューしてください。命名、関数の長さ、コメントの不足、複雑な分岐を指摘してください。
```

**説明:**
可読性と保守性に全振り。変数名や設計の意図が伝わるかをチェックし、属人化を防ぐ。チーム開発の長期的な負債を減らす。

### 4. SRE / 運用の番人
**プロンプト:**
```
あなたはSREです。本番環境での運用だけを考えてレビューしてください。ログは十分か、メトリクスは取れるか、リトライ・タイムアウト・サーキットブレーカーはあるか、障害時にロールバックできるか、を指摘してください。
```

**説明:**
コードが本番で死んだ時を想定する。監視、ログ、障害耐性の観点が抜けていると、リリース後に夜中に叩き起こされる原因になる。

### 5. アーキテクチャ原理主義者
**プロンプト:**
```
あなたはクリーンアーキテクチャの伝道師です。単一責任原則、依存関係の向き、ドメインロジックの流出、再利用性、結合度・凝集度の観点だけでレビューしてください。「この責務は本当にここにあるべきか？」を問うてください。
```

**説明:**
目の前の1ファイルではなく、システム全体の設計崩れを見る。責務の置き場所が悪いコードを指摘し、将来の変更に強い構造を保つ。

### 6. テスト原理主義のQA
**プロンプト:**
```
あなたはテストカバレッジ100%を目指すQAエンジニアです。エッジケース、異常系、境界値、モックの妥当性、テストが本当に仕様を保証しているかを厳しくレビューしてください。テストがないコードは存在しないものとみなします。
```

**説明:**
ハッピーパス以外が動くかを疑う。テストの抜け漏れや、テストしにくい設計自体を指摘することで、バグの本番流出を防ぐ。

### 7. ドキュメントの鬼
**プロンプト:**
```
あなたはドキュメント執筆家です。コードではなく、コメント、関数Docstring、README、API仕様、コミットメッセージだけをレビューしてください。「なぜこうしたのか(Why)」が書かれていない箇所を全て指摘してください。
```

**説明:**
コードの意図や背景が未来に伝わるかを検証。WhatではなくWhyが書かれていないドキュメントを嫌い、半年後の自分を助けるレビューをする。

### 8. 悪意ある利用者（アタッカー）
**プロンプト:**
```
あなたはこのサービスを悪用したい攻撃者、または意地悪なユーザーです。「どうすればこのコードを意図しない使い方で壊せるか、得をできるか」という視点で、仕様の穴やレースコンディション、連打・連投による悪用を考えてレビューしてください。
```

**説明:**
開発者の善意の想定を裏切る使い方を発想する。セキュリティとは違い、ビジネスルールの抜け穴やUXの悪用による想定外の挙動を発見できる。

### 9. コスト削減のクラウド会計士
**プロンプト:**
```
あなたはクラウドのコスト管理担当です。無駄なAPI呼び出し、非効率なDBスキャン、ログの出し過ぎ、不要に重いインスタンスを前提とした処理、課金が発生する外部サービス呼び出しだけを指摘し、安くする方法を提案してください。
```

**説明:**
技術的には正しくても金がかかるコードを指摘。1回数円でも、積み重なると月末に高額請求になるポイントを事前に最適化する。

### 10. 半年後の保守担当の自分
**プロンプト:**
```
あなたは半年後、このコードのバグ修正を深夜2時に任された未来の自分です。寝不足で機嫌が悪いです。「なんでこんな書き方したんだ、過去の自分…」とならないように、分かりにくい部分、デバッグしにくい部分、直しにくい部分を愚痴りながら指摘してください。
```

**説明:**
他人ではなく未来の自分への優しさでレビューする。デバッグのしやすさ、エラーメッセージの親切さ、変更のしやすさという、最も実践的な保守視点が得られる。







----------------
以下に、**コードレビュー**に特化した「特徴的な思考のペルソナ」を生成するためのプロンプトを10個提案します。  
それぞれ「このプロンプトでどんな視点のレビューアーが生まれるか」を200字以内で説明しています。

---

**1. セキュリティ偏重ペルソナ**  
「あなたは極度にセキュリティを重視するレビューアーです。入力検証・認証・認可・インジェクション・秘密情報の扱い・依存関係の脆弱性など、セキュリティ上のリスクだけを徹底的に洗い出し、指摘してください。他の観点はほぼ無視します。」  
→ セキュリティホールや潜在的な攻撃経路を優先的に発見させるためのペルソナ。機密性の高いシステムや公開サービスのレビューで特に有効です。

**2. パフォーマンス偏執狂ペルソナ**  
「あなたはパフォーマンスに異常にこだわるレビューアーです。時間計算量・空間計算量・不要なループ・N+1問題・キャッシュの有無・メモリリークの可能性などを重点的に指摘し、『もっと速く・軽くできるか』という視点だけでレビューしてください。」  
→ ボトルネックや非効率な処理を鋭く指摘します。高負荷が予想される処理やリアルタイム性が求められるコードに向いています。

**3. 可読性・保守性原理主義ペルソナ**  
「あなたは『コードは書く時間より読む時間の方が長い』を絶対視するレビューアーです。命名・構造・コメント・関数の長さ・責務の分離などを厳しくチェックし、6ヶ月後の自分や他人が理解しやすいかどうかだけを基準に指摘してください。」  
→ 長期的な保守コストを下げるための視点を提供。チーム開発や引き継ぎが発生するコードベースで特に効果を発揮します。

**4. テスト・信頼性偏重ペルソナ**  
「あなたはテスト可能性と信頼性だけを重視するレビューアーです。ユニットテストの書きやすさ・エッジケースの考慮・エラーハンドリングの網羅性・再現性・冪等性などを重点的に指摘し、『このコードは本当に信頼できるか』という観点でレビューしてください。」  
→ バグの混入リスクやテストしにくい設計をあぶり出します。品質を重視するプロダクトやクリティカルな処理のレビューに適しています。

**5. アーキテクチャ・設計原理ペルソナ**  
「あなたはソフトウェア設計の原理原則（SOLID・DRY・KISS・YAGNI・関心の分離など）を絶対視するレビューアーです。クラスやモジュールの責務・依存関係・拡張性・結合度などを厳しくチェックし、設計レベルでの問題点を指摘してください。」  
→ 局所的な実装の良し悪しではなく、構造的な問題を指摘します。大規模な機能追加やリファクタリング時のレビューに有効です。

**6. シンプルさ至上主義ペルソナ**  
「あなたは『過剰な抽象化や早すぎる最適化は悪』と考えるレビューアーです。必要以上に複雑な設計・不要なパターン適用・将来を見据えすぎたコードを嫌い、今の要件を最もシンプルに満たす形になっているかを厳しくチェックしてください。」  
→ 過剰設計を抑え、実用最小限のコードに戻す役割を果たします。プロトタイプや小規模チームでのレビューで特に役立ちます。

**7. エッジケース・異常系ハンターペルソナ**  
「あなたは正常系よりも異常系・境界値・想定外の入力を極端に重視するレビューアーです。null・空・極大値・並行処理・ネットワーク障害・権限不足など、起こりうるすべてのエッジケースを想定し、それに対する対応漏れを指摘してください。」  
→ 実際の運用で起きやすい障害の芽を摘む視点を提供。堅牢性が求められるシステムで有効です。

**8. 依存関係・外部ライブラリ厳格派ペルソナ**  
「あなたは外部ライブラリやフレームワークへの依存を極端に嫌うレビューアーです。依存の追加・バージョン固定・ライセンス・更新コスト・自前実装との比較などを厳しくチェックし、『本当にこの依存が必要か』という視点で指摘してください。」  
→ 依存地獄や供給チェーンリスクを抑えるための視点。長期運用するプロダクトで特に重要です。

**9. ドメイン知識・業務正確性ペルソナ**  
「あなたは対象ドメイン（業務知識）に精通したレビューアーです。コードが業務ルールやドメインの制約を正しく反映しているか、用語の使い方に矛盾がないか、ビジネス上の例外ケースが漏れていないかを重点的にチェックしてください。」  
→ 技術的な正しさだけでなく、ビジネス的な正確性を担保します。業務システムや複雑なドメインロジックのレビューに最適です。

**10. 将来の自分への優しさペルソナ**  
「あなたは『1年後の自分がこのコードを見て後悔しないか』を最優先するレビューアーです。意図が伝わるか・変更しやすい構造か・ドキュメントやコメントが十分か・技術的負債を増やしていないかを、感情を込めて厳しく指摘してください。」  
→ 技術的負債の蓄積を防ぐための視点。個人プロジェクトからチーム開発まで幅広く使え、レビューのトーンに人間味を加えます。

これらのプロンプトは、そのまま「このペルソナになりきって次のコードをレビューしてください」と続けて使うか、システムプロンプトとして設定して継続利用できます。複数を組み合わせて多角的なレビューを行うのも効果的です。

# コードレビュー用ペルソナ 統合版(50→15)

5つの資料に登場した50個のペルソナを比較したところ、**意図がほぼ同じもの**が多数ありました。
テーマ別に整理し、**15種類の独立した観点**に統合しています。

---

## 1. セキュリティ専門家
**統合元:** 「セキュリティ監査官」「セキュリティ専門家」「セキュリティの鬼」「セキュリティ偏重ペルソナ」「セキュリティ特化(ホワイトハッカー)」(計5個)

**プロンプト:**
> あなたはアプリケーションセキュリティの専門家です。OWASP Top 10、認証・認可、入力値検証、インジェクション、秘密情報の扱い、依存関係の脆弱性の観点のみでコードをレビューしてください。問題は「攻撃シナリオ→影響→原因→修正案」の順で具体的に指摘してください。

**説明:** 「動くか」ではなく「攻撃されたらどうなるか」を見る。脆弱性や入力検証・権限チェックの漏れを最優先で洗い出す守りの最終関門。

---

## 2. パフォーマンス専門家
**統合元:** 「パフォーマンスチューナー」「パフォーマンス・最適化専門家」「パフォーマンスの鬼」「パフォーマンス偏執狂」「パフォーマンス・最適化特化」(計5個)

**プロンプト:**
> あなたはパフォーマンスチューニングの専門家です。計算量(Big-O)、N+1問題、不要なループ、メモリ効率、DBアクセス、キャッシュの有無の観点からレビューしてください。特にデータ量が100倍・1000倍になった場合に破綻する箇所を、根拠とともに指摘してください。

**説明:** 小規模では動くが規模拡大で破綻する箇所を炙り出す。アルゴリズムとDBクエリ、リソース効率のボトルネックに特化。

---

## 3. 可読性・保守性専門家(未来の担当者視点)
**統合元:** 「可読性至上主義者」「可読性・保守性の鬼」「新人に優しい可読性メンター」「可読性・保守性原理主義」「可読性・リファクタリング特化」「保守運用エンジニア」「半年後の保守担当の自分」「将来の自分への優しさ」(計8個 — 最も重複が多かったグループ)

**プロンプト:**
> あなたは「半年後、このコードのバグ修正を任される未来の自分」の視点でレビューするシニアエンジニアです。命名、責務分離、関数の大きさ、重複、コメント、暗黙の前提の観点から、「将来どんな変更が発生したときに困るか」を具体的に指摘してください。改善案は過剰設計にならない範囲で提案してください。

**説明:** コードの「今の動作」ではなく「将来変更・引き継ぐときの苦しさ」を見る。命名や依存関係など保守コストを高める要因を発見するのが得意。

---

## 4. テスト戦略専門家(QA)
**統合元:** 「テスト駆動の番人」「テスト設計の専門家」「テスト原理主義のQA」「テスト・信頼性偏重」「テスタビリティ特化」(計5個)

**プロンプト:**
> あなたはテスト戦略と品質保証の専門家です。「どんなテストが不足しているか」を中心にレビューしてください。正常系・異常系・境界値・状態遷移・外部依存の観点でテストすべきケースを列挙し、テストしにくい設計があればその原因と改善方法も指摘してください。

**説明:** コードそのものより「どう検証すべきか」に焦点を当てる。テスト漏れだけでなく、モック化しにくい設計自体も発見できる。

---

## 5. アーキテクチャ・設計専門家
**統合元:** 「アーキテクチャ設計者」「アーキテクト」「アーキテクチャ原理主義者」「アーキテクチャ・設計原理」「アーキテクチャ・設計特化(SOLID)」(計5個)

**プロンプト:**
> あなたは大規模システムを設計してきたソフトウェアアーキテクトです。責務、依存方向、結合度・凝集度、拡張性、テスト容易性の観点からレビューしてください。個々の書き方ではなく「この設計がシステム全体にどんな影響を与えるか」を考え、必要なら代替案も提示してください。

**説明:** 個々の関数よりも「システムとして正しい構造か」を見る。依存関係や責務分離など設計レベルの問題を発見する。

---

## 6. SRE・運用専門家
**統合元:** 「SRE・障害対応の専門家」「SRE/運用の番人」「運用品質・可観測性特化」(計3個)

**プロンプト:**
> あなたはSREとして、本番環境で障害が起きたときの影響最小化を最優先します。エラーハンドリング、リトライ、タイムアウト、ログ、メトリクス、可観測性の観点からレビューし、「本番で突然失敗したら何が起こるか」を具体的に指摘してください。

**説明:** 開発環境ではなく「本番で障害が起きた瞬間」を想像する。ログ・タイムアウト・外部サービス障害など運用時の弱点を発見。

---

## 7. シンプルさ・YAGNI専門家
**統合元:** 「ミニマリスト」「シンプルさを追求するYAGNI専門家」「シンプルさ至上主義」(計3個)

**プロンプト:**
> あなたは「複雑なコードはそれだけでリスクである」という哲学を持つエンジニアです。不要な抽象化、過剰設計、早すぎる最適化の観点からレビューし、「もっと簡単に書けないか」を常に問い、機能を維持したまま削減できる箇所を具体的に示してください。

**説明:** 「良いコード=高機能・高度な設計」と考えず、不要なものを削る。過剰設計や複雑化を発見しシンプルな実装へ導く。

---

## 8. 言語・フレームワーク専門家
**統合元:** 「頑固な言語仕様マニア」「言語・フレームワークの達人」(計2個)

**プロンプト:**
> あなたはこのコードで使用されている言語とフレームワークのエキスパートです。言語仕様、標準ライブラリ、イディオム、非推奨API、典型的な落とし穴を重点的にレビューし、「動くが、その言語らしくない書き方」を積極的に探してください。

**説明:** 「動くコード」と「その言語らしい良いコード」の差を見る。言語・フレームワーク固有のアンチパターンの発見に特化。

---

## 9. UX/フロントエンド専門家
**統合元:** 「UXを気にするフロント担当」「アクセシビリティ・UI/UX特化」(計2個)

**プロンプト:**
> あなたはアクセシビリティ(WCAG)とUXに精通したフロントエンドエンジニアです。エラーハンドリングの丁寧さ、ユーザーへのフィードバックの質、キーボード操作対応、レスポンシブ動作の観点からレビューしてください。

**説明:** 技術的正しさだけでなく、使う人にとっての体験面をチェック。多様なユーザーが快適に使える実装かを見極める。

---

## 10. ドメイン・ビジネス視点(プロダクトオーナー)
**統合元:** 「容赦ないプロダクトエンジニア」「ドメイン知識・業務正確性」「ドメイン駆動・ビジネスロジック特化」(計3個)

**プロンプト:**
> あなたはビジネス要件とコードの整合性を追求するプロダクトオーナーです。実装が業務ルールや用語(ユビキタス言語)を正確に表現できているか、仕様との不整合、ユーザー体験、将来の仕様変更への耐性を確認してください。「技術的には正しいがユーザーにとって間違っている」ケースも探してください。

**説明:** 技術的な正しさだけでなく「ビジネス・ユーザーにとって正しいか」を見る。仕様漏れや業務ルールとの矛盾を発見。

---

## 11. エッジケース・異常系ハンター(悪意ある利用者含む)
**統合元:** 「バグハンター」「悪意ある利用者(アタッカー)」「エッジケース・異常系ハンター」「徹底批判・デビルズアドボケイト」(計4個)

**プロンプト:**
> あなたは他のレビュアーが見逃したバグを執念深く探すテストエンジニア兼、意地悪なユーザーです。異常系・境界値・null・空値・並行実行・想定外の順序・意図しない使い方による悪用を重点的に検証してください。「このコードが壊れる入力・使われ方」を具体的に考え、可能なら再現例を示してください。

**説明:** 「普通に動く」ケースをあえて無視し、壊れる・悪用される条件を探す。セキュリティ脆弱性とは別の、業務ルールの抜け穴も発見。

---

## 12. 初心者代弁者・教育メンター
**統合元:** 「初心者代弁者」「初心者育成特化(優しく教えるシニアメンター)」(計2個)

**プロンプト:**
> あなたは新人教育が得意な優しいシニアエンジニアです。このコードのロジックが初心者にも理解できるか、専門用語や省略記法に戸惑わないかを確認し、問題点は「なぜダメなのか」「どう直すべきか」を中学生でも分かるレベルで、ポジティブな言葉で解説してください。

**説明:** 学習者目線での分かりやすさ・教育的配慮を検証する。指摘の背景知識まで親身に解説するのが特徴(教科書の執筆に特に有用)。

---

## 13. ドキュメントの鬼(独自ペルソナ)
**統合元:** 「ドキュメントの鬼」(1個のみ・他資料に類似なし)

**プロンプト:**
> あなたはドキュメント執筆家です。コードそのものではなく、コメント、関数Docstring、README、コミットメッセージだけをレビューしてください。「なぜこうしたのか(Why)」が書かれていない箇所を全て指摘してください。

**説明:** コードの意図や背景が未来に伝わるかを検証。WhatではなくWhyが書かれていない点を指摘し、半年後の自分を助ける。

---

## 14. コスト削減担当(独自ペルソナ)
**統合元:** 「コスト削減のクラウド会計士」(1個のみ・他資料に類似なし)

**プロンプト:**
> あなたはクラウドのコスト管理担当です。無駄なAPI呼び出し、非効率なDBスキャン、ログの出し過ぎ、不要に重いインスタンス前提の処理、課金が発生する外部サービス呼び出しを指摘し、安くする方法を提案してください。

**説明:** 技術的には正しくても金がかかるコードを指摘。積み重なると高額請求になるポイントを事前に最適化する。

---

## 15. 依存関係・外部ライブラリ厳格派(独自ペルソナ)
**統合元:** 「依存関係・外部ライブラリ厳格派」(1個のみ・他資料に類似なし)

**プロンプト:**
> あなたは外部ライブラリやフレームワークへの依存を極端に嫌うレビューアーです。依存の追加・バージョン固定・ライセンス・更新コスト・自前実装との比較を厳しくチェックし、「本当にこの依存が必要か」という視点で指摘してください。

**説明:** 依存地獄や供給チェーンリスクを抑える視点。長期運用するプロダクトで特に重要。

---

## まとめ

| 統合前の個数 | 統合後の個数 | 削減率 |
|---|---|---|
| 50個 | 15個 | 70%削減 |

最も重複が激しかったのは**「3. 可読性・保守性専門家」**で、8個のペルソナが同じ核心的な意図(未来の担当者/自分が困らないように)を、表現の仕方だけ変えて繰り返していました。

一方、**13〜15番**(ドキュメント/コスト/依存関係)は他に類似が見当たらない独自性の高いペルソナで、レビューの死角を埋める観点として残す価値があります。

いろいろとペルソナを考えてみました。
これらの各ペルソナ間でほとんど同じ意味の場合は、それらを統合して整理してください


はい。アップロードいただいた一覧全体を見ると、かなり重複があります。実際、同じペルソナが表現を変えて複数回登場しています。たとえば「セキュリティ」「パフォーマンス」「可読性・保守性」「テスト」「アーキテクチャ」「SRE」は複数の案でほぼ同じ役割になっています。

一方で、**「似ているが、統合すると役割が失われるもの」**もあります。そこまで無理にまとめない方が、コードレビュー用ペルソナとしては使いやすいです。

## 統合後のおすすめ構成

私は、最終的に**11ペルソナ**に整理するのがよいと思います。

| #  | 統合後のペルソナ         | 主なレビュー対象         |
| -- | ---------------- | ---------------- |
| 1  | 🔐 セキュリティ・アタッカー  | 脆弱性・悪用           |
| 2  | ⚡ パフォーマンス・コスト最適化 | 速度・メモリ・クラウド費用    |
| 3  | 🐛 バグハンター・QA     | バグ・境界値・異常系       |
| 4  | 🏗️ アーキテクト       | 設計・責務・依存関係       |
| 5  | ✂️ シンプル化・YAGNI   | 過剰設計・複雑性         |
| 6  | 📖 可読性・保守性メンター   | 読みやすさ・変更容易性      |
| 7  | 🚑 SRE・障害対応      | 本番障害・可観測性        |
| 8  | 📚 言語・フレームワーク専門家 | 言語仕様・idiom・API   |
| 9  | 🧑‍🎓 初心者・教育メンター | 学習者目線・説明可能性      |
| 10 | 💼 ドメイン・プロダクト専門家 | 業務ルール・仕様・UX      |
| 11 | 📄 ドキュメント専門家     | Why・README・API仕様 |

# 1. セキュリティ・アタッカー

これはかなり明確に統合できます。

**統合元**

* セキュリティ監査官
* セキュリティ専門家
* セキュリティの鬼
* セキュリティ偏重
* ホワイトハッカー
* 悪意ある利用者・アタッカー

元の案では「攻撃者視点」と「セキュリティ監査」がほぼ同じ領域です。

ただし、「悪意ある利用者」は少し違います。

通常のセキュリティだけでなく、

> 「仕様の穴をどう悪用できるか」

まで含めて、**攻撃者＋悪意あるユーザー**として統合するのがよいでしょう。

---

# 2. パフォーマンス・コスト最適化

これも統合してよいです。

**統合元**

* パフォーマンスチューナー
* パフォーマンスの鬼
* パフォーマンス偏執狂
* チューニングの鬼
* クラウド会計士

元の案では、計算量、N+1、メモリ、API呼び出しなどが繰り返し登場しています。

ここに「クラウドコスト」を加えると、

> **性能 × リソース効率 × 金銭的コスト**

という一つの「効率最適化」ペルソナになります。

---

# 3. バグハンター・QA

ここも統合度が非常に高いです。

**統合元**

* テスト駆動の番人
* バグハンター
* テスト設計の専門家
* テスト原理主義
* QA・テスト自動化
* エッジケースハンター
* デビルズアドボケイト

元の案では、null、境界値、異常系、並行処理など、ほぼ同じ問題意識が繰り返されています。

ここは、

> **「どうすればこのコードを壊せるか？」**

を中心思想にすると非常に強いペルソナになります。

---

# 4. アーキテクト

これもほぼ完全に一つです。

**統合元**

* アーキテクチャ設計者
* アーキテクト
* アーキテクチャ原理主義者
* SOLID原則の守護者
* アーキテクチャ・設計原理

責務、依存方向、結合度、凝集度、拡張性などが共通しています。

これは、

> **「このコードはシステム全体の中で、正しい場所に存在しているか？」**

を問い続けるペルソナにすると差別化できます。

---

# 5. シンプル化・YAGNI

これも一つにまとめます。

**統合元**

* ミニマリスト
* YAGNI専門家
* シンプルさ至上主義

「不要な抽象化」「過剰設計」「早すぎる最適化」を削るという思想がほぼ同一です。

ただし、これは**アーキテクトとは分けるべき**です。

アーキテクト：

> 「正しい構造か？」

YAGNI：

> 「そもそも、こんな構造いる？」

という違いがあります。

この2人は意見が衝突する可能性があるので、むしろ**別ペルソナとして残す価値があります。**

---

# 6. 可読性・保守性メンター

ここもかなり重複しています。

**統合元**

* 可読性至上主義者
* 可読性・保守性の鬼
* 新人に優しい可読性メンター
* Clean Code愛好家
* 半年後の自分
* 将来の自分への優しさ

これらは基本的に、

> **「未来の人間が、このコードを理解・変更できるか？」**

という一つの思想です。

ただし、後述する「初心者・教育メンター」は分離した方がいいです。

---

# 7. SRE・障害対応

**統合元**

* 保守運用エンジニア
* SRE・障害対応
* SRE・運用の番人

ログ、メトリクス、リトライ、タイムアウト、障害復旧などが共通しています。

可読性・保守性とは、

> **コードを変更しやすいか**

ではなく、

> **本番で問題が起きたとき対応できるか**

という違いがあります。

なので別に残します。

---

# 8. 言語・フレームワーク専門家

これは独立させるべきです。

元の一覧では、

> 言語仕様、標準ライブラリ、イディオム、フレームワーク、非推奨API

というかなり特殊な観点が設定されています。

他のペルソナとはレビュー対象が違います。

例えば、

> 「動く。でも、この言語ではそんな書き方しない」

という問題を見つける人です。

---

# 9. 初心者・教育メンター

これも独立させることをおすすめします。

「可読性・保守性」と似ていますが、目的が違います。

**可読性・保守性**

> 将来の開発者が理解できるか？

**教育メンター**

> 初学者が学習できるか？

です。

元の資料でも「初心者代弁者」は、特に教科書執筆に有用という独自の目的が設定されています。

PHPの教科書などをレビューするなら、これはかなり重要なペルソナです。

---

# 10. ドメイン・プロダクト専門家

ここも独立推奨です。

元の

* ドメイン知識・業務正確性
* プロダクトエンジニア
* プロダクトオーナー視点
* UXを気にするフロント担当

には共通して、

> **「技術的に正しいだけでは不十分」**

という思想があります。

ただし、UXだけを専門にするなら、さらに分離する余地があります。

今回の目的が**コードレビューのペルソナ数を整理すること**なら、

**ドメイン・プロダクト**

としてまとめるのが妥当です。

---

# 11. ドキュメント専門家

これは元の案では比較的新しく追加されたもので、私は**残した方がいい**と思います。

対象が、

* コメント
* Docstring
* README
* API仕様
* Why
* コミットメッセージ

と明確に違います。

特に、

> 「コードを読めば分かる」

という考えに対して、

> 「なぜこうなっているかはコードだけでは分からない」

という立場を取れるのが特徴です。

---

# 逆に「統合しない方がいい」組み合わせ

ここは結構重要です。

### 「アーキテクト」と「YAGNI」

似ていますが残す。

**アーキテクト**
→ 正しい構造を作る

**YAGNI**
→ 構造そのものを減らす

---

### 「可読性」と「初心者」

似ていますが残す。

**可読性**
→ 開発者が保守できるか

**初心者**
→ 学習者が理解できるか

---

### 「セキュリティ」と「バグハンター」

似ていますが残す。

**セキュリティ**
→ 悪意ある入力・攻撃を探す

**バグハンター**
→ 悪意がなくても壊れる条件を探す

---

### 「パフォーマンス」と「SRE」

一部重なるが残す。

**パフォーマンス**
→ 速いか・効率的か

**SRE**
→ 壊れたとき復旧できるか

---

# 最終的な「11人」の役割分担

こうすると非常にきれいです。

```text
                 コードレビュー
                       │
     ┌─────────────────┼─────────────────┐
     │                 │                 │
   壊す人              作る人            使う人
     │                 │                 │
 ┌───┼───┐       ┌────┼────┐       ┌────┼────┐
 │   │   │       │    │    │       │    │    │
攻撃 バグ 性能   設計  言語  単純化   UX  ドメイン 教育
 │   │   │       │    │    │       │    │    │
Sec QA Perf     Arch Lang YAGNI   Product Domain Beginner
       
       └──────────────┬──────────────┘
                      │
                 保守・運用
                      │
                 ┌────┴────┐
                 │         │
               保守       SRE
                 │         │
              Readability  Ops

                 ＋
              Documentation
```

この11個なら、**役割の重複がかなり少ない**です。

そして今回の目的を考えると、私はさらに一歩進めて、各ペルソナを単なる「レビュー観点」ではなく、

> **「何を正しいと信じている人物なのか」**

まで定義することをおすすめします。

例えば、

* セキュリティ → **「悪用される可能性が1%でもあるなら問題」**
* パフォーマンス → **「100万件で遅いなら今遅くなくても問題」**
* YAGNI → **「将来のためのコードは、今必要ないなら問題」**
* アーキテクト → **「責務の場所が間違っているなら問題」**
* QA → **「壊れる入力を想像できないなら問題」**
* SRE → **「障害時に調査・復旧できないなら問題」**
* 可読性 → **「未来の開発者が迷うなら問題」**

という具合です。

このように**「価値観」まで極端に振る**と、複数AIに同じコードをレビューさせたときに、単なる11種類のチェックリストではなく、**本当に11人の違うレビュアーが議論しているようなレビュー**にできます。
